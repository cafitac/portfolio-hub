1. 음성 — 말이 끝났는지 판단하기

문제
생각하느라 잠깐 멈춘 것을 답이 끝난 것으로 보면, 답이 중간에 잘린 채 채점돼요. 반대로 오래 기다리면 대화가 굼떠요.
왜 어려웠나
iOS Safari 는 음성 인식기가 마이크를 쥐고 있어 소리 크기나 별도 음성 모델을 쓸 수 없고, 받아쓴 글자만 남아요. 한국어는 「~습니다」로 문장이 끝나도 말이 이어지는 일이 많아요.
어떻게 풀었나
  • 규칙은 언제 물어볼지만 정하고, 말이 정말 끝났는지는 LLM 응답의 keep_listening 이 최종 판정해요. 규칙 = 거름망, 모델 = 판정으로 나눴어요.
  • 문장 끝 뒤 대기 시간을 훑어(2.6초 15.7% · 3.0초 9.0% · 3.4초 3.7% · 3.8초 0%) 잘림 목표 5% 아래에서 가장 짧은 3.4초를 골랐어요.
  • 공개 오디오 말끝 모델(SmartTurn 류)은 그림자 모드로 붙여 비교하고, 동의한 목소리만 모아 한국어 모델을 학습할 준비를 해 두었어요.
숫자
설명형 답 잘림 69.7% → 3.7%, 실제 사건 재현 1/2 → 0/2. 대신 설명형 답의 대기는 1.60초 → 3.75초로 늘었고, 대화 모드는 2.85초 → 1.60초로 줄었어요.

2. iOS — 음성만 네이티브로 다시 짜기

화면은 웹을 그대로 쓰고, 웹에서 풀 수 없던 음성만 앱이 맡아요.

웹(Safari)에서의 문제앱에서
짧은 침묵에 인식 세션이 끊기고 다시 켜는 틈에 말을 잃어요네이티브 세션은 화면이 멈출 때까지 끊지 않아요
한국어 고정이라 TCP · UDP 같은 영어 CS 용어가 한글로 깨져요iOS 26 SpeechAnalyzer 에 CS 용어 · 지금 질문을 힌트로 줘요
코치가 말하는 동안 마이크가 꺼져 끼어들 수 없어요마이크와 코치 목소리를 한 오디오 엔진에 올려 에코를 지우고, 읽는 중에도 듣다가 끼어들 수 있어요
소리 크기를 몰라 생각 중 멈춤과 말끝을 구분 못 해요에코를 지운 마이크 소리 크기를 웹의 말끝 판단에 넘겨요

시스템 설계 면접용 Apple Pencil 캔버스(PencilKit)도 같은 방식으로 붙였어요 — 손그림을 올리면 빠진 부분을 정답 대신 질문으로 되물어요.

3. 면접관 하네스 — 모델은 제안, 코드가 결정

문제
모델에게 면접 진행을 통째로 맡기면 같은 걸 계속 파거나, 너무 빨리 넘어가거나, 끝낼 때를 놓쳐요.
어떻게 풀었나
  • 턴마다 모델은 판정과 다음 발화를 한 번의 호출로 제안만 해요. 더 파기 · 화제 틀기 · 다음 질문은 코드의 라우터가 정하고, 꼬리 질문은 최대 4번이에요.
  • 꼬리 질문 깊이는 사실 → 이유 → 대안 → 한계 → 원리 순서를 코드가 강제해요.
  • 화면 6개에 흩어진 꼬리 질문 예산 · 답 나누기 · 판정 기준을 공통 엔진(고르기 → 나누기 → 채점 → 꼬리 → 증거) 하나로 모으고 있어요. 패키지 경계는 테스트로 막아 거꾸로 의존하지 못하게 했어요.

4. 비동기 작업과 실시간 통로 — 오래 걸리는 답을 잃지 않기

문제
채점처럼 오래 걸리는 모델 호출이 웹 프록시(90초) · Cloudflare(100초)보다 길어지면, 서버는 끝까지 돌아 저장했는데 화면은 "요청에 실패했습니다"를 봤어요. 실제로 90.9초 걸린 요청에서 그랬어요.
어떻게 풀었나
  • 답 보내기를 202 접수 + 공통 작업 실행기로 바꾸고, 결과는 탭마다 SSE 연결 하나로 밀어 줘요. 연결이 안 되면 같은 모양의 폴링으로 돌아가요.
  • 같은 답을 다시 보내도 두 번 채점하지 않게 요청 키에 유니크 인덱스를, 같은 대상이 동시에 두 번 돌지 않게 status = 'running' 부분 유니크 인덱스를 걸었어요.
  • 도는 서버가 10초마다 하트비트를 남기고, 60초 넘게 소식이 없으면 서버가 내려간 것으로 보고 "다시 보내기"로 닫아요. 작업 하나의 모델 호출 예산은 180초예요.
  • 과제 리뷰 · CS 면접 · 학습 대화 · 시스템 설계가 같은 모듈을 써요.

5. 검색 — 숫자가 좋아도 바로 켜지 않기

구성
질문의 근거(공고 · 기술 블로그 · 이력서)를 찾는 검색은 별도 서비스(knowledge)이고, 벡터 계산은 상태 없는 임베딩 서비스(로컬 Qwen3-Embedding)가 맡아요. 서버만 내부 토큰으로 부를 수 있어요.
실험
질의를 여러 갈래로 늘리는 확장을 켜면 MRR 0.810 → 0.833 · 0.883, 상위 3개 안에 정답 84.6% → 92.3% 로 나아졌어요. 하지만 늘린 질의가 실행마다 달라 결과가 흔들려서 기본값은 끄고, 평가 실행에서만 골라 써요.
그 밖에
검색 결과 중복 제거로 MRR 0.927 → 0.939.

6. 운영 — 멈춤 장애를 끝까지 추적하기

증상
배포 직후 CPU 는 0% 인데 서버가 아무 요청에도 답하지 않는 멈춤이 반복됐어요.
추적
연속 실패가 쌓이면 스레드 덤프를 한 번 남기는 감시 장치를 먼저 붙였고, 재발했을 때 덤프로 원인을 찾았어요 — JDK 21 가상 스레드가 Jackson · kotlin-reflect 의 synchronized 잠금을 쥔 채 캐리어 2개를 모두 붙잡아(pinning), 잠금을 넘겨받을 스레드가 올라탈 자리가 없었어요.
해결
런타임을 JDK 25(JEP 491 — synchronized 안에서도 캐리어를 내려놓음)로 올리고 캐리어를 8개로 늘렸어요. 감시 장치와 liveness 검사는 그대로 두었어요.
격리
계정 격리 QA 체크리스트로 작업 · 실시간 통로 · 진행 안내에서 남의 데이터가 보이는지 확인하고, 남의 연습 id 에 "지금 채점 중"이 드러나던 문제를 고쳤어요.
