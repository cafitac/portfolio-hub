thread-example · 기술 노트

장애를 먼저 재현하고 숫자로 고친 기록

스레드형 커뮤니티 백엔드예요. 기능을 다 만들고 튜닝하는 대신, 합성 트래픽 봇으로 부하를 올려 병목이 실제로 드러난 뒤에만 고쳤어요. 사건마다 증상 → 원인 → 선택지 → 결정 → 전후 숫자를 결정 기록(ADR) 37건에 남겼고, 이 페이지는 그중 다섯 개를 옮긴 거예요.

모든 수치는 합성 부하 실험에서 잰 값이에요. 실제 사용자 트래픽이 아니에요.

실험 조건

traffic bot생각 시간 · 인내심 · 재시도가 있는 가상 사용자 수만 명
gatewaynginx · 1코어
appJava 21 · Spring Boot · 2코어 4GB 고정
dbPostgreSQL · 1코어

관측: Prometheus · Grafana · cAdvisor · 요청 추적 로그 — 매 실험은 같은 출발선(산술식 시드)에서 계단식으로 부하를 올리고, 봇이 잰 사용자 체감 값으로 판정한다

서버 사양은 일부러 작게 고정했어요. 하드웨어를 늘려 덮지 않고, 병목을 코드 · 쿼리 · 설정에서 찾게 하려는 조건이에요.

사건 1. 목록 조회 하나가 앱 전체를 멈췄다

증상
부하를 올릴수록 처리량이 오히려 줄었어요(155 → 122 rps). p95 는 수백 ms 에서 4초대로, GC 60% · 커넥션 대기 181 인데 DB CPU 는 0.1 이었어요.
가설
페이지 없는 GET /threads 가 요청마다 글 1만 건을 읽고 직렬화해 GC 를 부르고, CPU 를 잃은 스레드가 커넥션을 쥔 채 기다려 나머지가 줄을 선다.
확인
고치기 전에 반증 실험부터 했어요. 목록 조회를 빼지 않고 다른 행동으로 바꿔 요청 수 · 사용자 수를 같게 두었어요 — 빼기만 하면 "가벼워져서 나아졌다"와 구분되지 않아요. 결과: 처리량이 부하에 정비례(83 → 2,617 rps), GC 60% → 1%, 커넥션 대기 181 → 0. 커넥션 대기는 DB 문제가 아니라 CPU 를 잃은 스레드의 결과였어요.
결정
페이지 나누기. 추천안은 커서였지만, 오프셋으로 시작하고 깊은 페이지 비용을 측정으로 다시 확인하는 쪽을 골랐어요. 나중에 커서로 옮겨 다음 페이지 쿼리를 0.105ms → 0.030ms 로 줄였어요.
전후
처리 한계 약 160 → 4,503 rps(약 28배), 같은 부하에서 p95 5ms.

사건 2. 피드를 개인화하자 처리량이 13배 떨어졌다

증상
전역 피드를 "내가 팔로우한 사람의 글"로 바꾸자 버티는 동시 접속이 75,000 → 10,000 명으로, 처리량이 13배 떨어졌어요. DB CPU 는 다 쓰지도 못했고 DB 시간의 78.1% 가 피드 첫 페이지였어요.
원인
실행 계획이 최신 글부터 거꾸로 훑으며 내 피드에 들어갈 글을 만날 때까지 버렸어요 — 21개를 채우려고 158,702행. 팔로우가 적은 사람일수록 더 깊이 팠어요.
선택지
쿼리 모양피드 첫 페이지
인덱스 없음16.8ms
인덱스 + IN · 합쳐서 정렬0.31ms
인덱스 + 사람별 최신 21개(LATERAL) — 채택0.17ms
결정
LATERAL 을 고른 이유는 속도보다 상한이에요. 사람마다 최신 21개만 읽으니 비용이 "팔로우 수 × 21"로 묶여요. 인덱스를 만들어도 계획기는 여전히 PK 역스캔을 골라서(통계가 팔로우와 최신 글의 상관을 모름), 쿼리 모양으로 계획을 강제했어요. 처음부터 쓸 때 밀어넣기(fan-out on write)로 만들지 않은 것도 일부러예요 — 단순한 것을 먼저 재야 다음 설계를 숫자로 설명할 수 있어요.
전후
피드 첫 페이지 16.8ms → 0.103ms(163배), 같은 1만 명에서 307 → 1,274 rps, 버티는 동시 접속 1만 → 3만 명, DB 시간 비중 78.1% → 2.1%. 병목은 팔로워 수 세기로 옮겨 갔어요 — 다음 사건이에요.

사건 3. 서버는 한가한데 gateway 가 연결을 거절했다

증상
처리량이 꺾이는 지점을 넘자 연결 약 7,000 개에서 nginx 가 새 연결을 못 받아 에러가 96.7% 가 됐어요. 그때 앱 · DB CPU 는 거의 0 이었어요. 로그: "worker_connections are not enough".
원인
워커 수 auto 가 컨테이너의 1코어 제한을 모르고 VM 코어 수(8)만큼 떠서 연결이 고르게 퍼지지 않았고, 워커당 연결 1,024 · 파일 한도 1,024 · keep-alive 65초가 겹쳤어요.
결정
워커 1 · 워커당 연결 16,384 · 파일 한도 65,536 · keep-alive 15초(생각 시간 평균 8초인 사용자의 85% 가 연결을 그대로 씀). 앱 쪽도 upstream keep-alive 64 → 256, Tomcat 연결당 요청 상한 해제.
전후
연결이 7,071 에서 막히던 것 → 36,052 까지 거절 없이 열렸어요. 다만 그 지점을 넘으면 이번엔 봇 쪽 재시도 폭주로 14초 안에 무너져요 — 고친 것과 남은 것을 같이 적었어요.

사건 4. 커넥션 풀은 공식이 아니라 측정으로

맥락
동시 접속 5만에서 Tomcat 스레드 200/200, 풀 대기 188. 풀 크기는 설정한 적이 없었어요(기본값 10). 흔히 권하는 계산(코어 수 × 2 + 디스크 수)대로면 1코어 DB 에는 3~4 예요.
실험
풀 크기처리 rps사용자 p95
4 (공식값)6,33773ms
10 (기본값)6,33647ms
20 — 채택6,34716ms
402,97810,000ms — 무너짐
해석
처리량은 DB 1코어가 정해서 같았고, 공식값이 가장 나빴어요. 공식은 "커넥션을 쥔 시간 = DB 가 CPU 를 쓰는 시간"을 가정하는데, 실제로는 BEGIN · COMMIT 왕복과 객체 변환 동안 DB 는 놀아요. 40 에서는 커넥션 한 번 쥐는 시간이 약 30배로 늘어 재시도 연쇄로 무너졌어요.

사건 5. 인기 글 한 행에 좋아요가 줄을 섰다

증상
풀을 80 으로 키우자 like_count 갱신이 DB 시간의 40% 를 썼어요. 인기 글 하나의 행 잠금에 모든 좋아요 트랜잭션이 줄을 섰고, 커넥션을 늘리면 줄이 앱에서 DB 안으로 옮겨 갈 뿐이었어요.
선택지
세지 않고 매번 count(*)(인기 글에서 비쌈, 이미 버림) · Redis 카운터(저장소가 늘고 두 저장소의 정합성이 새 문제) · DB 안의 원장.
결정
좋아요는 원장에 행을 추가만 하고, 1초마다 모아 한 번에 반영해요. 꺼내기와 더하기를 한 트랜잭션에 묶어 두 번 더하지도 잃지도 않게 했어요. 인기 글에 1초 동안 500개가 와도 그 행 갱신은 1번이에요.
전후
좋아요 갱신이 쓰던 DB 시간 225,762ms(40.3%) → 10,279ms(4.4%), 22배. 버티는 동시 접속은 흔들림 안에서 그대로(5.5만 ~ 6만) — 병목이 잠금 대기에서 DB CPU(피드 쿼리)로 옮겨 갔어요.

그 밖의 결정 기록

사건이 아니어도 고르고 이유를 남긴 것들이에요.

  • 멱등성 키는 DB 제약으로 지킨다 — 서버는 성공, 클라이언트는 실패로 아는 불일치를 막기. 기록이 3,370만 행 · 14GB 쌓인 걸 보고 24시간 보존으로
  • Tomcat 스레드는 기본값 200 유지 — 줄였더니 서버 p95 는 19 → 5ms 로 좋아졌지만 사용자 p95 는 그대로였다. 줄 서는 자리가 옮겨졌을 뿐
  • synchronous_commit 은 on 유지 — 성공 응답을 받은 쓰기를 잃지 않는다
  • 앱 사양 1코어 → 2코어 4GB — 1코어에서는 JVM 이 Serial GC 를 골랐다는 사실을 확인하고
  • 운영 콘솔 — 동시 접속 · 처리량 · p95 · 에러율과 사건 기록을 한 화면에
  • Kubernetes 이전 — 작은 PR 단위로 옮기고, 예산은 namespace 쿼터 + 전용 코어로 지킨다
